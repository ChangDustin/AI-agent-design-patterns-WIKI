## 1. LLM 的提案

### 這篇在講什麼

1. **先分清楚兩種系統。** Anthropic 把所有這類系統統稱為「代理式系統（agentic systems）」，再分成兩種：
   - **工作流程（workflow）**：LLM 和工具照著**事先寫好的程式路徑**走。
   - **代理（agent）**：LLM **自己決定**流程和要用哪些工具。
2. **能簡單就簡單。** 先找最簡單的解法，必要時才增加複雜度，甚至可能完全不需要代理式系統。代理式系統是用延遲和成本換表現；很多應用只要把單次 LLM 呼叫配上檢索和範例調好就夠了。→ 這正好補上第 1 篇留下的「什麼時候別用」缺口。
3. **小心框架。** 建議先直接呼叫 LLM API，很多模式幾行程式就寫得出來。框架的抽象層會把底下的 prompt 和回應藏起來，讓除錯變難，也讓人忍不住加上不必要的複雜度。真要用框架，就要懂它底下的程式在做什麼。
4. **基本積木：增強型 LLM（augmented LLM）**＝LLM＋檢索＋工具＋記憶。
5. **五種工作流程模式：**
   - **提示鏈（prompt chaining）**：一步接一步，每次呼叫處理上一步的輸出，中間可以加程式檢查的「閘門（gate）」。例：先寫大綱 → 檢查大綱是否合格 → 依大綱寫全文。
   - **路由（routing）**：先分類，再交給專門的後續流程。例：客服問題分成一般、退款、技術支援；簡單的問題給小模型，困難的給大模型。
   - **平行化（parallelization）**：分段（把任務切開同時做）或投票（同一件事做多次）。例：一個模型回答、另一個同時把關不當內容；多個提示一起審查程式漏洞。
   - **協調者—工作者（orchestrator-workers）**：一個中央 LLM 動態拆任務、分給工作者 LLM、再整合結果。跟平行化的差別在於子任務不是事先定好的。
   - **評估者—優化者（evaluator-optimizer）**：一個生成、一個評估並給回饋，反覆循環。適合條件：評估標準清楚，而且改進能被衡量。
6. **代理的本質很單純：** 在迴圈裡，根據環境回饋使用工具的 LLM。每一步都要從環境拿到「實際結果」（工具結果、程式執行結果）來判斷進度；可以在檢查點停下來問人；要設停止條件（例如最多幾輪）。適合步驟數無法預測、路徑寫不死的開放問題；代價是成本較高、錯誤會一路累積。
7. **三原則：** 簡單、透明（把代理的規劃步驟攤開給人看）、用心設計「代理—電腦介面（ACI）」，也就是把工具的說明寫清楚並測試過。
8. **工具也要做提示工程：** 格式要貼近模型平常在網路上看到的寫法（例如程式碼放在 markdown 裡，比塞進 JSON 要跳脫字元容易）；工具要做**防呆（poka-yoke）**。例子：他們的 SWE-bench 代理常把相對路徑搞錯，改成強制用絕對路徑後就沒再出錯。他們花在調工具上的時間，比調整體 prompt 還多。
9. **實務上最有價值的兩個應用：** 客服（對話＋查資料＋退款等動作，成效可衡量）、寫程式（能用自動測試驗證；但人工審查仍然必要）。

### 想問作者的問題

1. **用詞怎麼統一？** 我建議 Wiki 採用 Anthropic 的區分當正式定義（比較精確，對初學者也好懂）。Ng 的四種模式則定位成「零件」，可以組成工作流程，也可以組成代理。「代理式工作流程」那頁保留，但加註說明。
2. **比喻**：工作流程 vs. 代理＝**跟團旅行 vs. 自由行**（延續「規劃＝排行程」的旅行比喻）。跟團路線固定、穩定可預期；自由行邊走邊決定，彈性大，但可能迷路、花費也比較高。
3. **頁面粒度**：五種工作流程裡，四種各開一頁；「評估者—優化者」併進「反思」頁當別名。Wiki 先收完整，簡報不一定全講。還是你偏好合成一頁「五種工作流程」總表？
4. **和我們的 pipeline 的張力**：Anthropic 建議先直接呼叫 API，小心框架讓 prompt 不透明，而我們選了 LangGraph。我的對策是 LangGraph 只管流程（節點和邊），LLM 呼叫直接用 aisuite＋Groq，每次的 prompt 和回應都寫進執行紀錄。要把這個取捨寫進 LangGraph 頁（之後也可以放進反思）嗎？
