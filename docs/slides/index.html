代理式工作流程

代理式工作流程不要求 LLM 一次生成最終答案，而是安排多步驟、多次呼叫，逐步改好作品。①

  • 適合需要高品質、會反覆修改的任務，如寫作、寫程式、做研究。①
  • 代理式系統會增加延遲與成本，若單次呼叫配合檢索已足夠，可不必使用。①
  • 在 HumanEval 程式題上，加入代理迴圈可把成功率提升至 95.1%。①
打個比方：Zero‑shot像不准倒退的寫作文，代理式像先列大綱再修正。①

四種招式一次看

Ng 2024 將 AI 代理分為反思、工具使用、規劃與多代理協作四種招式。①

  • 反思 Reflection：自行檢查、修改，穩定度高。①
  • 工具使用 Tool Use：使用計算機、上網查，穩定度高。①
打個比方：就像寫作文：先列大綱（規劃），查資料（工具使用），寫草稿再自我校正（反思），最後請同學互相批改（多代理協作）。②

反思：自己改作文

讓 LLM 檢查自己剛產出的結果、提出具體改進建議，再依建議重寫（Ng 2024）。①

  • Self‑Refine 在 7 種任務上平均提升 20%，最高 40%（Madaan 2023）。②
  • GPT‑4 對話偏好分數從 25.4% 提升至 74.6%（Madaan 2023）。②
  • 數學推理提升有限，僅從 92.9% 到 93.1%（Madaan 2023），非萬靈丹。②
打個比方：寫完作文先自己訂正一次，或請同學幫忙挑毛病，再改出第二版。①

反思實作：心形圖貼文

  1. 1

    需求

    說明要畫心形圖並寫成貼文，列出關鍵要素。①

  2. 2

    初稿

    請 LLM 產生程式碼與貼文草稿。②

  3. 3

    評論

    把產出貼回模型，請它從正確性、風格、效率等面向給建設性批評。②

  4. 4

    第二版

    依批評重寫程式碼與貼文，完成最終貼文。①

工具使用：帶計算機

給大型語言模型（LLM）一組可「請求呼叫」的函式，讓模型只產生呼叫指令，真正的運算或動作由外部程式執行。①

  • 在提示中先說明每個工具的功能與參數需求。①
  • 模型判斷需要工具時，輸出特定格式的呼叫請求。①
  • 外部程式執行工具，將結果回傳給模型繼續處理。①
打個比方：就像考試允許帶計算機或字典，計算機負責算術，模型只決定什麼時候使用它，而不必自己心算。①
本頁依據 Wiki：①工具使用（Tool Use）

麥茶20杯夠不夠？

  1. 1

    介紹工具

    在提示中說明 quote_order 函式功能與參數（商品、數量）①

  2. 2

    提出請求

    模型輸出 JSON 請求 {tool:quote_order, item:麥茶, qty:20}①

  3. 3

    程式執行

    外部 Python 讀取請求，計算總價 600 元②

  4. 4

    結果回傳

    把計算結果 600 元送回模型，模型回覆「夠，還剩 200 元」②

規劃：出國排行程

規劃是讓 LLM 自己決定要依序執行哪些步驟，將大任務拆成小任務完成（Ng 2024）。①

  • LLM 先收到一個大目標，再把它拆成可執行的子任務（Ng 2024）。①
  • 拆任務後，LLM 寫結構化計畫，列出每步工具與輸入輸出（Ng 2024）。①
  • 執行遇問題時，代理即時改路，關鍵點停下請人確認防失控（Anthropic 2024）。①
打個比方：就像出國前排好行程：先決定景點與順序，現場若關閉再即時調整。①

ReAct：想→做→看

  1. 1

    想法

    模型文字推理下一步，如拆解目標或處理例外，只在上下文思考。①

  2. 2

    動作

    模型執行任務，如 search、lookup 或 finish，取得資訊。①

  3. 3

    觀察

    讀回環境回應，如 Wikipedia 前5句或天氣預報，供下輪想法。①

多代理：分組報告

多個「代理」分工合作、互相討論，產出比單一代理更佳結果，通常以不同提示讓同一或多個 LLM 扮演不同角色。①

  • 研究顯示，多代理系統在內部評測中比單一代理好 90.2%。①
  • 為達成更好效果，token 用量約是單代理的 15 倍。①
  • 運作步驟包括拆角色、寫提示、各自執行、互相溝通、避免傳話遊戲。①
打個比方：就像分組報告：有人查資料、有人做投影片、有人檢查，最後由組長整合成完整報告。①
本頁依據 Wiki：①多代理協作（Multi-agent Collaboration）

跟團vs.自由行

工作流程

  • 路線由旅行社排好，穩定、可預期①
  • 適合任務能事先拆成固定步驟的情況①
  • 例：先寫大綱 → 程式檢查 → 依大綱寫全文①

代理

  • 邊走邊決定下一站，彈性大但可能迷路、花費較高①
  • 適合步驟無法事先寫死，需要模型自行決策①
  • 例：SWE‑bench 代理自行決定要改哪些檔案①
本頁依據 Wiki：①工作流程 vs. 代理（Workflow vs. Agent）

能簡單就簡單

工作流程讓 LLM 按事先寫好的程式路徑執行；代理讓 LLM 自己決定下一步與使用的工具。①

  • 先試最簡單：單次 LLM 呼叫配檢索與範例，往往已足夠。①
  • 若步驟可事先寫死，選工作流程以獲得穩定結果；若無法寫死，改用代理取得彈性。①
打個比方：工作流程像跟團旅行，行程固定可預期；代理像自由行，邊走邊決定下一站，彈性大但可能迷路。①

代理也會出包

代理把 LLM 放入多步驟、可行動系統，放大其上下文有限、長程規劃不穩、格式不可靠等弱點。①

  • 上下文塞不下且成本高：大量歷史或 API 回傳超出字數上限，錯誤累積會增加 API 費用。①
  • 自評盲點：在專業領域 LLM 無法辨識自己的錯誤，評估結果可能不可靠。①
  • 卡在迴圈：代理可能重複產生相同想法或動作，難以跳脫，常見於 ReAct 框架。①
打個比方：就像一位能幹的實習生：資料放不下、計畫被打亂會慌、報告格式偶爾錯，需主管把關。①
本頁依據 Wiki：①代理的限制與風險
16

AI做事，人來把關

在代理或工作流程的關鍵位置安排人來檢查、修改或決定，讓錯誤能及早被發現和修正，而不是只看最後的成品。①

  • 把代理的規劃步驟、想法或中間成果攤開，讓過程可見。①
  • 在關鍵檢查點暫停，請人回饋並可直接修改中間成果。①
  • 最終由人決定是否採用結果，並做人工測試找出自動評估漏掉的問題。①
打個比方：就像實習生寫報告，主管先在大綱階段看一次方向，最後定稿前再檢查一次，避免整份報告跑錯方向。①
